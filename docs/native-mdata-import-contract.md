# Native MData: импорт и Recovery

Read-only аудит действующего Python-контракта и текущих Rust/C++ компонентов. Это карта следующей реализации, а не подтверждение готовности native import/Recovery. Пользовательские профили, WinCred и MAX в ходе аудита не открывались.

## Три формата, два разных способа применения

| Вход | Подтверждённое поведение Python | Что нельзя потерять при переносе |
| --- | --- | --- |
| Компактный `.mdata`, `MXMODMD\x02` | Добавить только отсутствующие авторизации: `access_token_<ID>@MXMOD` и необязательный `auth_<ID>` | Не заменять существующий профиль, БД, общие ключи, историю и настройки. Старая папка/метаданные без непустого токена допустимы. |
| Старый `.maxsession`, `MXMODSA\x01` | Полностью проверить контейнер, преобразовать auth-файлы и токены; только добавление | Нельзя трактовать как восстановление полного профиля. |
| Полный `.mdata`, `MXMODMD\x01` | Добавление отдельных аккаунтов либо восстановление профиля; предварительно полный зашифрованный backup и Recovery-маркер | Отдельная политика файлов/ключей и транзакция. При legacy add существующие `auth_<ID>`/`user<ID>` нового аккаунта — `profile_collision`, в отличие от компактного импорта. |

Preview намеренно принимает только компактный v2. Он не доказывает возможность применить старый полный архив. Восстановление Recovery читает полный backup из проверенного маркера, а не произвольный путь из QML.

## Компактное добавление: обязательный порядок

1. Проверить выбранный локальный путь, пароль и подтверждённый fingerprint без доступа к текущим авторизациям. Preview уже аутентифицирован, но его результат не заменяет проверку входа непосредственно при импорте.
2. Под общим `Local\MAXModSessionTransferV1` дождаться полного завершения всех потенциально использующих MXMOD клиентов. Неизвестный путь/неполное перечисление не означает «клиентов нет». Старый контракт: до 120 секунд, непрерывно 2 секунды без клиентов. Затем разобрать архив в ограниченную приватную память/стадию; проверить terminal + EOF, весь manifest и точные размеры auth-файлов. SHA-256 **тех же прочитанных байтов контейнера** должен совпасть с preview; замена файла/формата означает `source_changed`. Повторить closed-check непосредственно перед применением.
3. Получить только имена собственных token-targets, читать значения по точным именам. Активен только **непустой native access_token**. Различать отсутствующий target и существующий пустой blob. Общие, history, calls, web и `@ONEME` значения для компактного импорта не читаются.
4. Уже активные входящие ID оставить без изменений, даже если архив содержит другой токен. Нет новых ID → `already_present`, 0 записей. Проверить объединённый лимит 3 активных аккаунта до любых изменений.
5. Предварительно проверить **все** новые ID. Существующий обычный `user<ID>` сохранить и удержать его идентичность, не обходя содержимое. Существующий безопасный `auth_<ID>` до 256 КиБ сохранить байт-в-байт, даже если он пустой, устарел, не является JSON или отличается от архива. Небезопасный тип/ссылка/подмена недопустимы.
6. Если локального auth нет, а во входе есть — создать эксклюзивно, записать, flush/fsync, сохранить identity и ожидаемые байты. Ещё раз проверить сохранённые auth/user объекты и отсутствие неожиданно появившихся объектов. **Только после этого** записать новый токен с ожидаемым предыдущим состоянием `None` либо `Some(empty)`.
7. На обычной ошибке откатить только собственные изменения в обратном порядке. Запись включать в журнал **до** потенциально изменяющего вызова: native API может успеть записать и затем вернуть ошибку. Явный pre-write конфликт `destination_not_empty` исключает эту запись из журнала: нельзя удалить чужой токен даже с совпадающими байтами.

Откат токена требует совпадения ожидаемого значения; восстановление пустого target должно вернуть пустой target, а не удалить его. Удаление собственного auth требует и прежней identity, и прежних байтов. Изменённый/заменённый объект сохраняется, результат — `rollback_failed`. Ошибка cleanup/записи диагностического статуса не превращает успешное добавление в провал и не маскирует исходную ошибку.

У компактного добавления нет обещания атомарности нескольких аккаунтов при отключении питания: может сохраниться корректное подмножество. Токен идёт после auth; повторный импорт дополняет незавершённые аккаунты. Нельзя заменять это поведением «стереть профиль и восстановить всё».

## Полный профиль и Recovery

- Отдельная allowlist включает собственные access/history/calls/common/web ключи и разрешённые файлы профиля. Ограничения Python: до 10 000 файлов и 4 ГиБ; logs/crashdumps/временные служебные файлы исключаются. БД history требует соответствующего `history_storage_key`; общая app-БД — common storage key; web-ключ должен принадлежать известному владельцу.
- До первого plaintext sink резервируется место под staging, служебные расходы и будущий backup. Неверный пароль/неаутентифицированный manifest не разрешают использование заявленных архивом размеров. Полный backup может содержать **ноль активных аккаунтов**: он нужен и для отката к пустому профилю.
- После полного authenticated decode и проверок создать зашифрованный полный backup текущего профиля. До первой мутации файлов/ключей опубликовать durable Recovery-маркер. При restore заменить импортированный `config.json` на pinned native `launcher_config.make_config`, сохранив принятые настройки изоляции/приватности.
- Restore: журнал ожидаемых credential-значений + перемещение только проверенных собственных каталогов с identity. Add: перенос только разрешённых данных новых аккаунтов; common/global данные текущего компьютера остаются. Не переносить механически старый `_apply_credentials`: там журнал дополняется после вызова; native версия должна учитывать возможный post-commit failure, как компактный importer.
- При успешном применении или полном успешном откате очистить **точно свой** маркер. `rollback_failed`, невозможность очистки маркера, частичный/повреждённый маркер → `recovery_required`; сохранить необходимые стадии, не запускать клиент автоматически.
- Recovery начинается только явной кнопкой. Открытие окна/чтение статуса не читает токены/архив и ничего не восстанавливает. Под тем же mutex: проверить закрытые клиенты, прочитать маркер, расшифровать указанный backup, проверить storage/config, повторить closed-check, восстановить, очистить точный маркер. После успешного восстановления ошибка запуска клиента не должна разрешить повторное восстановление по старому действию.

## Что уже есть и что ещё отсутствует

| Компонент | Состояние на момент аудита |
| --- | --- |
| `mdata_archive.rs`, `session_archive.rs` | Проверка/шифрование контейнеров и terminal/EOF; это не применение профиля. |
| `mdata_login.rs`, `mdata_preview.rs`, `mdata_preview_file.rs` | Строгая компактная схема, публичный authenticated preview, безопасное чтение выбранного файла; runtime сейчас предоставляет `mdata.inspect`. |
| `mdata_recovery_state.rs`, `launcher_config.rs`, `settings_io.rs` | Маркер read/write/exact clear, pinned конфигурация, проверенные пути и атомарная публикация отдельных файлов. Нет restore-транзакции. |
| `login_credentials.rs`, `transfer_lock.rs`, `mdata_login_capture.rs` | Новые исходники уже появились параллельно аудиту; в прочитанном снимке `lib.rs` ещё не подключены. Exact token adapter/различение пустого blob/кооперативный mutex/bounded live capture. Это не полный credential adapter для legacy restore. |
| `native/launcher/{activation,preflight,transfer_mutex}` | Полезны проверенные Win32/payload/lock примитивы. Activation проверяет конкретное окно, **не заменяет** полный closed-client scan по всем корням. |
| `MDataTransport.qml` | Direct Bridge, inspect; status `available:false`, import/export finite unsupported. Полный native импорт или Recovery не объявлены готовыми. |

Следующие законченные части, по порядку:

1. **Компактный transaction backend** (`mdata_login_import`): общий ограниченный authenticated decode, trait credentials, файловые identity/журнал/rollback. Сначала mock credentials + собственные тестовые MXMOD; реальный WinCred не нужен для доказательства алгоритма.
2. **Одноразовый native transfer host и closed-client policy**: ограниченный приватный IPC, отдельный процесс переживает закрытие MAX; READY только после получения mutex. Пароль/токены не в аргументах, env, отчётах или промежуточном открытом файле. Внутрипроцессный worker плагина не переживает `closeMessenger`. Постоянный HTTP-сервер и порт 18973 здесь не нужны.
3. **Direct import UI/результат**: preview → подтверждение fingerprint → handoff → штатное закрытие. Одна операция, bounded wait/cancel, конечный несекретный результат. Закрытие QML/abort не должно уничтожать уже начатую файловую транзакцию; rollback/drain завершается владельцем операции. Это transfer-жизненный цикл, не реализация заблокированного раннего bootstrap gate.
4. **Legacy full-profile backend**: расширенный credential policy, безопасное дерево/staging/backup, storage validation, restore/add journal и собственные rollback-проверки. До него v1 честно остаётся unsupported, не попадает в компактный importer.
5. **Native Recovery UI** поверх пункта 4 и готового `mdata_recovery_state`: пароль только после явного Restore, запрет повторного restore после успешного применения, конечный результат запуска. Старое ожидание освобождения HTTP-порта удалить; использовать native ownership/процессный результат без сетевого listener.

## Review in-process экспорта

Предложение **подходит для компактного MData**: explicit selection → single bounded worker → TransferLease → метаданные/проверка вместимости → capture → encryption → повторный capture → атомарное сохранение выбранного `.mdata`. Никаких закрытий/перезапусков клиента. Большой legacy backup для restore остаётся отдельным offline streaming-путём.

Mutex сериализует наши transfer-операции, но не останавливает обычные записи работающего MAX и не превращает WinCred read+write в CAS. Поэтому повторная проверка обязательна: одинаковый список auth, размеры **и байты**, одинаковые token-values, включая переход отсутствующий/пустой → активный. До публикации результат недоступен пользователю. Изменение источника допускает до 3 попыток с 50 мс паузой; не повторять ошибочный пароль, небезопасный путь, занятый destination или ошибку записи.

Компактный снимок ограничен 3 токенами по 2560 байт и 3 auth по 256 КиБ; manifest/ciphertext тоже должны иметь отдельный конечный cap. Поэтому допустимо шифровать в ограниченный memory buffer, затем записывать временный файл рядом с выбранным output. Только handle-owned no-overwrite rename после flush и последней проверки; при отмене/ошибке удаляется только собственный временный объект. Публикация — точка завершения: поздняя отмена не удаляет уже готовый пользовательский архив.

Существующий `GuardedStore.atomic_create` умеет no-overwrite publication, но не принимает callback revalidate перед rename. Для точной совместимости с export нужна небольшая checked-create/stream transaction API либо явно обоснованный ограниченный промежуток между финальным capture и публикацией; простая проверка только до шифрования недостаточна. `atomic_replace` здесь не подходит: существующий выбранный файл нельзя перезаписывать.

Сохранять проверку свободного места до чтения credentials: профиль и output, разные тома учитывать отдельно; legacy export reserve — 256 МиБ. Для bounded compact buffer достаточно повторной capacity-check перед commit. Constructor/status/job-validation остаются без чтения авторизаций. Комментарий нового `login_credentials.rs`, требующий закрытых клиентов и для capture, необходимо уточнить: закрытие обязательно для mutation/rollback; live export работает по вышеописанному snapshot-контракту.

## Минимальные приёмочные сценарии

| Область | Обязательные синтетические случаи |
| --- | --- |
| Authentication | Неверный пароль, повреждённый terminal, лишний EOF, duplicate keys, неверный размер, смена файла после preview: никаких credential reads/writes и никаких live-profile изменений. |
| Активность | Нет токена и пустой token-target не увеличивают счётчик активных аккаунтов; пустой target восстанавливается пустым при rollback. ID больше 2^53 остаётся строкой. |
| Сохранность | Stale user/auth сохраняются; auth другой/пустой/не-JSON допустим для компактного import; неправильный тип/reparse/hardlink/замена между проверками отклоняются. |
| Частичный сбой | Ошибка второго аккаунта, fsync, post-commit credential error, pre-write конфликт с теми же байтами, чужая замена auth/token во время rollback. Не удалять чужое, честно вернуть `rollback_failed`. |
| Повтор | Уже активный ID не перезаписывается; metadata-before-token после прерывания дополняется; четвёртый аккаунт отвергается до записи. |
| Host | READY не раньше mutex; неизвестный MAX-процесс блокирует mutation; закрытие UI не обрывает transaction; finite wait; нет пароля в command line/логах. |
| Legacy/Recovery | Empty backup, неправильный storage key, мало места, ошибка публикации/очистки маркера, частичный rollback, новый/чужой маркер не удаляется; успех restore + ошибка запуска не повторяет restore. |
| Live export | Изменение token/auth того же размера во время encrypt, stale → active, отказ последнего capture, destination уже существует, cancel до/после publish; ни close, ни restart, ни credential enumeration. |

Источники: `modkit/mdata_login.py` (`capture`, `import_snapshot`), `mdata_service.py` (`_export_login`, `_import_login`, `_import`, `_restore_all`, `recover_backup`), `mdata_manager.py`, `mdata_recovery.py`, `max_client_policy.py` и существующие `test_mdata_login.py`/`test_mdata_service.py`. Это аудит исходников; новых runtime/server-проверок он не заявляет.
