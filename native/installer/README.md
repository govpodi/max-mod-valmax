# Нативный установщик и обновление

В режиме `user-release` `valmax-native.iss` распространяет только готовый,
проверенный пакет. Production
компиляция требует `native-release-state.iss`: режим `user-release`, eligibility
1, число блокеров 0 и SHA-256 фактического `native-package.json`. Staging-пакет
не превращается в пользовательский установщик. Инструменты сборки могут
использовать Python; установленная программа и установщик его не запускают.

Проверка `user-release` дополнительно сверяет `STAGING-MATERIALS.json` с
точным inventory собранного runtime и требует `completeForWholeClient=true`
без оставшихся ограничений. Отдельный блокер
`max_redistribution_authorization` остаётся до проверки разрешения
правообладателя на публикацию изменённых исходников, ресурсов и установщика
MAX. Одни только зелёные тесты, булев флаг или утверждение пользователя не
подтверждают это право. Та же проверка нужна перед публикацией исходников в
публичный `main`; установочный preflight не управляет GitHub.

## Локальная preview-установка по явному запросу

Для ручного тестирования неполного переноса предусмотрен отдельный явный режим
`--distribution local-preview --version 8.9.0-native.preview.1`. Он не меняет
готовность public `user-release`: `releaseEligible=false`, все известные
продуктовые blockers сохраняются в manifest. Неизвестные blockers, ошибки
artifact validation, legacy localhost references и invalid evidence не
принимаются даже в preview. Полный inventory, matching launcher pins,
проверка target identity и зависимостей остаются обязательными.

Preview требует явно помеченную версию и закреплённый SHA документа
`native-preview.txt` на русском и английском. Мастер показывает его перед
установкой; документ остаётся в папке программы. Он перечисляет незавершённые
проверки retention/early-protection/installed-client и явно указывает, что
экспорт истории и медиа остаётся Бета и может быть неполным. Для публичного
релиза установленный экспорт должен подтвердить это предупреждение, медиа,
прогресс, задержку между запросами, отмену и обработку ошибок; доказательство
полного серверного архива не требуется. Имя в списке
приложений — `ValMAX native preview`, AppId и каталог ValMAX прежние, поэтому
применяется тот же managed upgrade с сохранением старого дерева и metadata.
Это установка локальной тестовой версии, не утверждение о завершении переноса.
Preview и публичный `user-release` используют lzma2 и solid compression,
чтобы уменьшить размер установщика. Сборка preview из-за этого занимает больше
времени.

`native/tests/installer/preview_compile_test.py` проверяет обе ветви настоящим
Inno `/O-`: Setup EXE не создаётся и не запускается. Production `user-release`
по-прежнему требует eligibility 1, blockers 0 и совпадающий manifest hash;
обычный `developer-staging` установщиком стать не может.

## Переключение целого дерева

До записи файлов установщик удерживает обычный `Local\MAXModSessionTransferV1`
mutex, проверяет принадлежащие каталогу процессы и обычность путей. Он не
завершает процессы. Учтены MAX, launcher, transfer helper, WebView2 и
`QtWebEngineProcess.exe`. Процесс вне точного каталога установки игнорируется. Если
процесс/путь невозможно достоверно проверить, операция останавливается.
Если WMI не сообщает путь sandbox-процесса, используется только
`PROCESS_QUERY_LIMITED_INFORMATION` и `QueryFullProcessImageNameW` по его PID.
Handle закрывается при любом исходе; память и командная строка не читаются,
пути процессов в диагностический журнал не выводятся. Неполученный путь
по-прежнему означает отказ. Fixture отдельно принудительно проверяет этот
fallback для собственного Unicode-пути с пробелами и внешнего похожего префикса.

Непустой каталог признаётся прежней установкой только при совпадении HKCU
uninstall AppId, точного InstallLocation, штатного uninstaller и контракта
нативного marker либо полного набора файлов старого `modkit/package_mod.py`.
Reparse points, зарезервированные пространства данных, неизвестный каталог и
ошибки перечисления не допускаются. Исключение — обычные каталоги
`.mxmod-helper-temp` старого launcher и его точный вариант
`runtime/.mxmod-helper-temp`: они остаются непрочитанными внутри backup;
его содержимое не обходится и не копируется в новую установку. Сам этот путь
и его дочерние пути нельзя выбирать в качестве каталога установки.
Содержимое пользовательских профилей,
ONEME/MXMOD и WinCred не читается и не изменяется.
Имя в регистрации должно точно принадлежать канонической семье `ValMAX` или
`ValMAX native preview`, включая известные русскую/английскую подписи версии.
Похожий префикс не принимается. Проверки AppId, пути, uninstaller и контрактов
файлов действуют независимо от имени. При проверке backup дерево устанавливает
собственный корень, поэтому opaque runtime helper сохраняется и при rollback.

Обновление не накладывает новые файлы на старые:

1. Точная собственная uninstall-ветка HKCU копируется с типами значений и
   подключами в отдельную ветку transaction. Записывается соседний журнал.
2. Целый старый каталог переименовывается в
   `<app>.valmax-backup-<transaction>`. Файлы Python и неизвестные файлы остаются
   в этой копии; новая программа получает чистый каталог и новый uninstall log.
3. После записи файлов и регистрации создаётся marker новой установки, журнал
   закрывается. Старое дерево и его metadata сохраняются. Успех разрешает
   postinstall-запуск; при ошибке его нет и exit code ненулевой.
4. При ошибке старое дерево и uninstall metadata возвращаются. Неполное новое
   дерево переименовывается в `<app>.valmax-incomplete-<transaction>`, а не
   удаляется. Следующий запуск установщика восстанавливает незавершённую
   transaction перед новой попыткой.

Первая установка тоже получает transaction: при ошибке частичные файлы
сохраняются рядом, незавершённая регистрация удаляется. Неизвестные файлы ни в
старом, ни в неполном дереве не удаляются. Удаление новой версии касается её
собственной описи и собственного marker; резервные копии и внешние данные
остаются. Автоматической очистки старых резервных копий нет.

После успешного обновления backup предназначен для восстановления целиком с
его uninstall metadata; это не вторая установка. **Не запускайте старый
uninstaller из backup-каталога:** его журнал содержит исходный путь установки.
Отдельный пользовательский мастер возврата к успешно заменённой версии ещё не
реализован; автоматический rollback покрывает сбой текущего обновления.

Журнал использует запись файла и переименование на том же томе. Проверено
восстановление после прерывания процесса; устойчивость при потере питания и
повреждении файловой системы не доказана. Если восстановление не удаётся,
установщик сохраняет журнал и деревья и прекращает работу.

## Проверки без настоящей установки

`native/tests/installer/managed_upgrade_test.py` компилирует и запускает настоящий
Inno installer только с отдельным fixture AppId и явно выбранным `--work-root`.
При ночной проверке каталог — `E:/ValMAXBuild/fixtures/installer-*`. В этом режиме отсутствуют ярлыки и
postinstall-запуск. Payload синтетический; MAX, профили и WinCred не участвуют.
Реальные тестовые процессы — отдельные программы, выполняющие только Sleep.

Сборка fixture процесса: MSVC x64 `/W4 /WX /O2 /MT` для
`native/tests/installer/fixture_process.cpp`, с объектами/EXE в
`E:/ValMAXBuild/build/installer-fixture-process-nightly`.

Пример запуска из корня проекта с build-only Python:

```powershell
$env:TEMP = 'E:\ValMAXBuild\tmp'
$env:TMP = $env:TEMP
& 'D:\CodexLabs\max-mod-26.35.1\venv\Scripts\python.exe' `
  native\tests\installer\managed_upgrade_test.py `
  --work-root E:\ValMAXBuild `
  --process-executable E:\ValMAXBuild\build\installer-fixture-process-nightly\ValMAX.exe `
  --report E:\ValMAXBuild\analysis\native-installer-upgrade-nightly.json
```

Тест проверяет реальную установку/обновление/удаление, rollback после копирования
и изменения HKCU, прерывание процесса после rename, отказ при занятом mutex,
работающем принадлежащем процессе, junction/неизвестном каталоге/плохом журнале,
миграцию старого контракта, побайтную сохранность backup и внешнего sentinel.
Production release gates проверяются только компилятором `/O-`; пользовательский
EXE из синтетического payload не выпускается.
